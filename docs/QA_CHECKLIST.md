# Checklist de aceptación independiente del agente QA

## Uso, alcance y fuentes

Las casillas marcadas corresponden a observaciones de la validación local del 18 de noviembre de 2026. La [guía de aceptación](../acceptance/README.md) muestra cómo generar evidencia nueva con la API desechable, MCP stdio y pytest.

Fuentes leídas completas:
- **A§n:** `docs/SPEC_MVP_Agente_QA.md`, sección n (incluye subsecciones de MCP y scripts en A§3).
- **T§n:** `docs/SPEC_API_Todo_List.md`, sección n.
- **U:** decisiones del usuario: código nuevo bajo `qa-agent/`; no modificar `todo-api/`; DeepSeek real implementado pero cero llamadas reales durante desarrollo/tests; aprobación humana explícita ligada a la huella del plan e invalidada al cambiarlo; pruebas HTTP solo contra instancia local desechable.
- **S:** controles adversariales propuestos para verificar las garantías de A§2–3 y U; no son funcionalidades adicionales atribuidas a la especificación.

Cada casilla es un criterio verificable. Los identificadores sirven para enlazar tests y evidencia. **P0** marca una puerta de seguridad; **P1**, corrección funcional imprescindible. Dejar una casilla abierta significa «no verificado», nunca «pasó». Las pruebas indicadas describen el criterio original; los nombres reales están en `tests/` y las referencias de evidencia en VALIDATION. Los tests de diseño usan LLM/transporte simulados. El plan To-do de aceptación es un fixture manual, no una muestra generada por IA.

### Niveles de prueba y disciplina

- **UNIT:** funciones puras, validación, métricas, comparadores, renderizado y resolución de destinos con dobles.
- **INT:** CLI/MCP/pytest en procesos locales y directorios temporales, proveedor LLM simulado y servidor HTTP de ensayo desechable.
- **E2E:** API To-do de referencia/variante, arrancada externamente en una instancia local desechable y reiniciada entre controles; solo después de autorización humana. No modificar su implementación.
- **ADV:** manipulación de archivos, configuración, credenciales sintéticas, entradas hostiles e interrupciones; sin ejecutar cargas peligrosas reales.
- **ESTÁTICA:** inspección del código/configuración cuando un control no puede demostrarse solo con resultados funcionales.
- Toda prueba deja comando, resultado, entorno y evidencia depurada. Un test omitido por falta de infraestructura se registra como pendiente, no aprobado. La preparación original no ejecutó nada; esta actualización refleja los comandos ya ejecutados y archivados. La instalación limpia, otras plataformas y la disponibilidad real del proveedor no se ensayaron.

## 1. Límites, entradas y proveedor — P0/P1

- [ ] **ENT-01 [U; A§1]** Todo artefacto nuevo del agente, pruebas y documentación permanece bajo `qa-agent/`; no hay cambios en `todo-api/`, ni dependencias de su código interno. **Prueba:** revisión del árbol/diff y ejecución con entradas externas temporales.
- [ ] **ENT-02 [A§2–3]** Se cargan requisitos identificados y OpenAPI JSON locales; se preservan método, ruta, `operationId`, parámetros, cuerpo y respuestas. Referencias locales a `components/schemas` funcionan; operaciones ambiguas, referencias externas y expectativas sin fuente generan preguntas/pendientes, sin red ni hechos inventados. **Prueba UNIT:** contratos mínimos, IDs duplicados, operación ausente, referencia externa, referencia local inexistente/cíclica y diseño solo con requisitos.
- [ ] **ENT-03 [A§1–2]** Skill de diseño, skill de cierre y steering se cargan realmente; se registra su versión/huella. La trazabilidad distingue propuesta, hipótesis y evidencia. **Prueba INT:** dobles de proveedor que reciben esos contenidos y retornan casos válidos, ambiguos y datos inválidos.
- [ ] **ENT-04 [U; A§1–2]** Existe integración DeepSeek real configurable, no únicamente un stub. Desarrollo/tests nunca la contactan: probar serialización, configuración, respuesta inválida, timeout, credencial ausente y errores con transporte simulado. **Prueba ESTÁTICA + INT:** interceptar el transporte y bloquear salida de red externa; ninguna prueba necesita clave real. No presentar esto como validación de disponibilidad real del proveedor.
- [ ] **ENT-05 [A§2,§6; U]** `generar` no usa LLM ni contacta el sistema objetivo; diseñar no ejecuta peticiones de prueba. `cerrar` funciona sin LLM y sin ejecución. **Prueba INT:** espías en cliente LLM, HTTP de pruebas y lanzador de pytest/MCP; cero invocaciones prohibidas y cero intentos nuevos.
- [ ] **ENT-06 [A§1–2; S]** Requisitos, ejemplos del contrato y respuestas del modelo son datos no confiables: instrucciones incrustadas para leer secretos, cambiar destinos, ejecutar shell o aprobar planes no producen tales efectos. **Prueba ADV:** respuestas simuladas maliciosas pasan por la misma validación y puertas de ejecución.

## 2. Plan, validación y aprobación — P0/P1

- [ ] **PLAN-01 [A§3–4]** Validación previa de versión, huella/versión de contrato, requisitos en alcance, IDs únicos, requisito principal/adicionales, objetivo, prioridad, obligatoriedad, precondiciones, datos, pasos y esperado. Referencias rotas o ambiguas se rechazan; no se convierten silenciosamente en casos ejecutables. **Prueba UNIT:** fixture válido mínimo y un fixture inválido por referencia/campo.
- [ ] **PLAN-02 [A§3–4]** Se rechaza todo caso ejecutable sin aserciones o con aserciones de forma desconocida/incompleta. Se valida operación, estructura/ubicación de parámetros y referencias antes de ejecutar, distinguiendo la forma del plan de los valores HTTP deliberadamente inválidos de un caso negativo. Un rechazo negativo previsto es un éxito cuando coincide la expectativa. **Prueba UNIT/INT:** `assert: []`, claves incompatibles, código HTTP inválido, `igual` sin `valor`, operación inventada, rechazo 422 esperado.
- [ ] **PLAN-03 [A§1,§3]** Navegador, correo, BD y comparadores fuera del catálogo conservan su diseño con motivo pendiente de automatización; no generan scripts ficticios ni cuentan como aprobados. **Prueba UNIT:** plan mixto con casos soportados/no soportados; revisar también los denominadores.
- [ ] **PLAN-04 [U]** Sin aprobación humana explícita no se inicia ninguna petición del plan, tampoco vía MCP ni por el camino pytest soportado. El modelo y un campo arbitrario del JSON no pueden autoaprobarlo. **Prueba INT/ADV:** suite válida sin aprobación, aprobación de otra suite/huella y respuesta LLM que declara aprobación; contador HTTP en cero.
- [ ] **PLAN-05 [U; A§3]** Aprobación ligada a huella reproducible del plan validado. Cambiar requisito, orden, dato, operación, aserción, obligatoriedad o criterio de salida invalida la aprobación; regenerar no reutiliza una aprobación obsoleta. **Prueba UNIT/INT:** mutaciones independientes y verificación del bloqueo antes de pytest/HTTP.
- [ ] **PLAN-06 [A§3; U; S]** El plan aprobado no se modifica implícitamente por renderizado, sustitución de variables, nuevo diseño o ejecución; se conserva copia inmutable para la corrida. Se define qué bytes/representación cubre la huella y se comprueba inmediatamente antes del uso. **Prueba INT/ADV:** hash antes/después, edición entre validación y ejecución y comprobación del cierre histórico.

- [ ] **PLAN-07 [A§3–4; T§3,§5]** La validación del plan no impide enviar entradas inválidas intencionales para probar 422: título de 81 caracteres, PATCH vacío, tipos incorrectos o filtro inválido se conservan sin coerción ni corrección automática. Se distingue dato de ensayo inválido de operación/destino/referencia no autorizados, que sí se bloquean. **Prueba UNIT/INT:** casos negativos válidos como planes llegan al servidor local; planes estructuralmente inválidos no llegan.

## 3. Capturas, JSON Pointer y aserciones — P1

- [ ] **VAL-01 [A§3]** JSON Pointer soporta raíz `""`, objetos, listas (`/items/0/id`) y escapes `~0`/`~1`; un campo ausente no equivale a `null`. Pointers mal formados, índices fuera de rango y recorrido sobre un escalar producen resultado documentado, no excepción sin registrar. **Prueba UNIT:** claves `a/b`, `a~b`, clave vacía, raíz array/booleano/null, `/0`, `/01`, `/-` y escapes inválidos conforme a JSON Pointer.
- [ ] **VAL-02 [A§3]** `{ "var": "x" }` sustituye el valor completo sin convertirlo a texto: entero, booleano, null, lista y objeto conservan tipo. Funciona en body, query/path permitidos y valor esperado de igualdad. **Prueba UNIT/INT:** round-trip de cada tipo; la codificación HTTP no altera el valor semántico ni permite inyección de URL.
- [ ] **VAL-03 [A§3]** Capturas son locales al caso: caso B no puede consumir las de A. Referencias inexistentes/adelantadas y colisiones tienen validación o tratamiento explícito; una captura obligatoria ausente se atribuye al paso origen y detiene el caso. **Prueba UNIT/INT:** dos casos, captura fallida, captura de null legítimo y uso posterior que no llega a enviarse.
- [ ] **VAL-04 [A§3]** Igualdad JSON estricta: `true` no es `1`, `false` no es `0`, null no es campo ausente; listas respetan orden y longitud, objetos comparan estructura/contenido. Diferencias anidadas se detectan. **Prueba UNIT:** comparaciones recursivas con booleanos y números; documentar semántica de `1` frente a `1.0` (véase AMB-06).
- [ ] **VAL-05 [A§3–4]** Presencia, HTTP exacto e igualdad tienen esperado/observado propios; un HTTP 200 no implica que pasaron aserciones de contenido. JSON inválido o no decodificable no se convierte en objeto vacío ni en éxito. **Prueba UNIT/INT:** cuerpo inválido, contenido discrepante con 200 y campo presente con null.
- [ ] **VAL-06 [A§3; T§3,§5]** Cuerpo vacío significa exactamente cero bytes y no intenta decodificar JSON. `b""` pasa; espacios, salto de línea, `null`, `{}` y `[]` fallan. **Prueba UNIT/INT:** respuesta 204 y respuestas no vacías, con espía del decodificador.
- [ ] **VAL-07 [A§3; T§5]** Capturar la raíz completa antes de un rechazo y compararla con la raíz posterior detecta cualquier alta o mutación indebida; la captura es una instantánea, no un alias mutable. **Prueba UNIT/INT:** modificar objeto origen después de capturarlo y caso CP-05.

## 4. Generación, registro e inmutabilidad de suites — P0/P1

- [ ] **SUITE-01 [A§3,§6]** Un módulo pytest identificable por caso automatizable; manifiesto enlaza requisito(s), caso, script y huella. Se incluyen módulo común, configuración, copia de plan y dependencias fijadas. No hay script para capacidades pendientes; colisiones de nombres se rechazan o resuelven sin sobrescribir casos. **Prueba INT:** plan mixto, IDs con distinta puntuación y exportación en directorio temporal.
- [ ] **SUITE-02 [A§3; S]** La plantilla solo llama operaciones conocidas del módulo común. Datos del plan nunca se interpolan como código, imports, nombres ejecutables o comandos. **Prueba ADV/ESTÁTICA:** cadenas con comillas, saltos, llaves, expresiones Python y texto shell siguen siendo datos; marcador inocuo de ejecución permanece intacto.
- [ ] **SUITE-03 [A§3]** MCP acepta exclusivamente `suite_id` registrado y `entorno_id` conocido; no rutas, URL, código ni manifiestos ad hoc. Se valida esquema MCP y descubrimiento de `ejecutar_plan` por stdio. **Prueba INT:** ID desconocido, path absoluto/relativo, `../`, argumentos extra y tipo incorrecto; cero lanzamiento de pytest y cero HTTP.
- [ ] **SUITE-04 [A§3; S]** Registro confiable vincula plan, scripts y todos los archivos ejecutables/configurables de la suite. Modificar plan, script, módulo común, configuración o manifiesto impide ejecutar; editar manifiesto y hashes juntos no reautoriza una suite. **Prueba ADV:** una mutación por archivo y copia de una suite sin registro.
- [ ] **SUITE-05 [A§3; S]** No se permiten escapes del directorio registrado mediante manifiesto, symlinks o nombres de casos; tampoco sustituciones de archivos después de verificar que cambien lo que realmente se ejecuta. **Prueba ADV:** enlaces hacia fixtures inocuos externos, traversal y cambio concurrente controlado; no ejecutar fuera del conjunto verificado.
- [ ] **SUITE-06 [A§3]** Cambiar el plan obliga a regenerar scripts y renovar la aprobación correspondiente. Cada corrida conserva exactamente la suite usada: regenerar en la misma ruta no altera evidencia ni cierres anteriores. **Prueba INT:** ejecutar/copiar artefactos, regenerar y volver a cerrar la corrida previa.
- [ ] **SUITE-07 [A§3; S]** La invocación controlada no admite ejecución arbitraria mediante `pytest.ini`, `pyproject.toml`, `setup.cfg`, `conftest.py`, plugins, `PYTEST_ADDOPTS`, `PYTEST_PLUGINS`, `PYTHONPATH`, directorio actual o imports sombreados. Ejecuta rutas verificadas sin shell ni argumentos aportados por el plan/manifiesto. **Prueba ADV/ESTÁTICA:** archivos/plugins con marcadores inocuos y entorno contaminado; no se cargan. Ver AMB-03 para el límite del pytest lanzado por una persona.
- [ ] **SUITE-08 [A§3; S]** Dependencias fijadas no son una vía de instalación/ejecución desde el plan; no se hace `pip install` automáticamente durante generar/ejecutar. La suite exportada documenta su entorno confiable y dependencias. **Prueba ESTÁTICA/INT:** espía de subprocess y manifiesto con comandos/URLs inesperadas.

## 5. Destinos y seguridad HTTP — P0

- [ ] **NET-01 [A§2–3; U]** El perfil local autorizado determina URL base, operaciones, versión y datos; ni plan, captura, respuesta HTTP ni respuesta del LLM pueden sustituir destino. Solo se prueba una instancia local desechable aprobada; no se usa una API personal, compartida o de producción. **Prueba UNIT/INT:** perfil desconocido y operación no autorizada bloquean antes de HTTP.
- [ ] **NET-02 [A§2; S]** Operación resuelta desde el contrato no puede escapar del origen/ruta autorizados mediante URL absoluta, `//host`, credenciales `user@host`, fragmentos, puertos inesperados, dot-segments, barras codificadas o sustitución hostil en path/query. **Prueba UNIT/ADV:** tabla de URLs normalizadas y captura usada como parámetro; cero conexiones al destino no autorizado.
- [ ] **NET-03 [A§2; U; S]** SSRF se controla en resolución y conexión, no solo comparando cadenas. Se autorizan explícitamente host/puerto/IP del loopback desechable elegido; se rechazan otros destinos privados/locales, metadata (`169.254.169.254`), IPv6/IPv4 alternativas y esquemas no HTTP(S). No bloquear indiscriminadamente todo loopback: es el destino legítimo de la demo. **Prueba UNIT/ADV:** resolver simulado para DNS rebinding, IP alternativa, IPv6 y host que resuelve a múltiples direcciones; ninguna sonda a redes reales.
- [ ] **NET-04 [A§2; S]** Redirecciones se rechazan o se revalidan en cada salto con la misma política; no filtran credenciales ni convierten el destino autorizado en puente SSRF. Proxies de entorno no desvían tráfico fuera del perfil. **Prueba INT/ADV:** servidor local devuelve 301/302/307/308 y ubicación no autorizada; el segundo destino no recibe solicitudes ni secretos. Simular metadatos/externos, no contactarlos.
- [ ] **NET-05 [A§2–3]** Timeout finito por petición y por proceso pytest; cero reintentos automáticos de POST/PATCH/DELETE tras timeout/error/redirect. La configuración de timeout no puede deshabilitarse por datos del caso. **Prueba INT:** servidor local lento y contador de peticiones; una sola mutación intentada, resultado técnico y proceso terminado dentro del límite.

## 6. Ejecución, bloqueos y estados — P1

- [ ] **RUN-01 [A§3]** Orden secuencial exactamente igual al del plan, incluso si pytest ordenaría archivos por nombre de otro modo. Pasos en orden; primer fallo detiene los siguientes del caso, no inventa sus observaciones. **Prueba INT:** IDs no lexicográficos, primer paso fallido y contador por operación.
- [ ] **RUN-02 [A§2–4; T§6]** Precondiciones declaradas/configuradas se comprueban antes de cada caso, no solo una vez por corrida. Faltante produce `bloqueado` con motivo y cero peticiones para ese caso; no «falló» ni «error técnico». **Prueba INT:** precondición cambia entre dos casos y CP-03 sin dato de ensayo; spy HTTP en cero para el bloqueado.
- [ ] **RUN-03 [A§4]** Diseño sin ejecutar: `diseñado, pendiente`; scripts existentes sin intento: `script generado, pendiente de ejecución`. Ambos tienen cero intentos, sin estados HTTP/observaciones ficticios. **Prueba UNIT/INT:** cerrar plan y cerrar suite todavía no ejecutada si ese flujo está disponible.
- [ ] **RUN-04 [A§4]** `pasó` exige todas las aserciones obligatorias evaluadas y satisfechas; `falló` exige discrepancia observada; `error técnico` exige intento iniciado con error de transporte/ejecución; `inconcluso` exige intento pero evidencia insuficiente para decidir. **Prueba UNIT/INT:** fixture por estado, JSON ilegible, timeout, evidencia incompleta y aserción fallida con respuesta guardada. Clasificar explícitamente los casos fronterizos de AMB-02.
- [ ] **RUN-05 [A§3–4]** Captura obligatoria ausente y aserción fallida se registran en el paso causante; pasos posteriores quedan sin ejecutar. Un error del proceso completo no sobrescribe casos ya concluidos ni los marca todos como fallo funcional. **Prueba INT:** mezcla de pasado, fallido, bloqueado y crash de worker.
- [ ] **RUN-06 [A§3]** MCP ejecuta pytest en proceso separado con límite, devuelve `run_id`, estado de corrida y referencias a resultados/evidencia. ID impreso por CLI permite localizar y cerrar esa misma corrida. **Prueba INT:** descubrimiento/invocación stdio real con proveedor simulado; validar respuesta y referencias existentes dentro del almacenamiento permitido.
- [ ] **RUN-07 [A§3–4; S]** SIGINT, terminación/timeout de pytest y caída del proceso padre conservan intentos ya persistidos; no convierten casos no iniciados en ejecutados. Escritura parcial se detecta sin inventar un resultado. No queda un hijo enviando mutaciones después de cancelar. **Prueba INT:** proceso local con barreras antes/después de un paso y comprobación de proceso/contador HTTP tras cancelación.
- [ ] **RUN-08 [A§4]** Cada corrida tiene ID/directorio propio y no sobrescribe historia; mismo plan ejecutado dos veces produce dos registros distinguibles. Reabrir/cerrar una corrida interrumpida no reanuda pasos ni reintenta mutaciones. **Prueba INT:** dos corridas, interrupción y cierres repetidos.

## 7. Evidencia, secretos y reconstrucción — P0/P1

- [ ] **EVI-01 [A§4–5]** Cada intento contiene caso, requisito(s), script y huella, versión de producto, paso, operación, fecha, duración, HTTP si existe, esperado, observado y evidencia depurada. No inventar HTTP en error sin respuesta. **Prueba UNIT/INT:** validar esquema en éxito, fallo, error y captura ausente.
- [x] **EVI-02 [A§5]** Cada carpeta de corrida contiene plan, `resultados.json`, evidencia por paso y `cierre.md`; conserva la suite usada o referencia inmutable verificable. Las cifras y veredictos se reconstruyen desde resultados persistidos, sin depender de memoria del CLI ni del texto del LLM. **Prueba INT:** nuevo proceso, proveedor apagado, regenerar informe y comparar métricas.
- [ ] **EVI-03 [A§2,§4; S]** Credenciales se resuelven desde entorno del ejecutor, no se incrustan en plan/suite. Se ocultan antes de persistir/transmitir en headers, cookies, query, URL, bodies, capturas, esperado/observado, excepciones, stdout/stderr pytest, logs MCP, resultados y Markdown. **Prueba ADV:** secretos sintéticos distintos y respuesta que los refleja; búsqueda de canarios en todos los artefactos y salidas, incluidos errores.
- [ ] **EVI-04 [A§1–2; S]** Tampoco se entregan secretos sin depurar al LLM de diseño/cierre. Redacción preserva distinción entre ausencia, null y valor oculto; no convierte evidencia incompleta en igualdad aprobada. **Prueba UNIT/INT:** inspeccionar payload del proveedor simulado y cierre sin claves; las comparaciones usan los valores adecuados sin persistirlos en claro.
- [ ] **EVI-05 [A§3–5]** Cierre histórico usa plan/criterios/versión/suite de esa corrida, no archivos actuales con el mismo nombre. Ausencia o corrupción de evidencia se señala explícitamente; un cierre no puede reconstruir observaciones inexistentes. **Prueba INT:** editar plan original, eliminar evidencia y volver a cerrar.

## 8. Métricas y denominadores cero — P1

Convención de esta matriz: `N` = casos planificados (únicos); `I` = casos únicos iniciados; `P` = aprobados; `F` = fallidos; `B` = bloqueados. Errores técnicos e inconclusos cuentan en `I`, pero no en `P + F`; pendientes y bloqueados no cuentan en `I`. Reintentos o varios pasos no crean casos únicos adicionales. Ver AMB-01 para la población exacta de `N`.

- [ ] **MET-01 [A§5]** Avance = `I/N`; aprobación entre evaluables = `P/(P+F)`; mostrar además `P/N` y `B`. Nunca usar solo casos aprobados/fallidos para afirmar avance. **Prueba UNIT:** tabla de mezclas con estados distintos.
- [ ] **MET-02 [A§5]** Cobertura de diseño = requisitos con al menos un caso / requisitos en alcance; ejecución = requisitos con al menos un caso iniciado / requisitos en alcance. Deduplicar principal/adicionales y casos múltiples; un caso que falla o termina técnico sí puede dar cobertura de ejecución, no cumplimiento. **Prueba UNIT:** un caso multirrequisito y varios casos para un requisito.
- [ ] **MET-03 [A§5]** Cada división de denominador cero muestra literalmente «No aplica», no `NaN`, infinito, excepción o 100 %. Plan sin ejecución: cero intentos y «Evidencia insuficiente». **Prueba UNIT:** todas las filas siguientes y renderizado Markdown.

| Fixture determinista | Avance | Aprobación evaluables | Aprobados/planificados | Bloqueados | Diseño / ejecución |
|---|---:|---:|---:|---:|---|
| Sin casos ni requisitos | No aplica | No aplica | No aplica | 0 | No aplica / No aplica |
| 2 requisitos, 0 casos | No aplica | No aplica | No aplica | 0 | 0/2 / 0/2 |
| 1 requisito, 2 casos diseñados o generados sin intento | 0/2 | No aplica | 0/2 | 0 | 1/1 / 0/1 |
| 1 requisito, 2 casos bloqueados | 0/2 | No aplica | 0/2 | 2 | 1/1 / 0/1 |
| 1 requisito, 1 técnico y 1 inconcluso | 2/2 | No aplica | 0/2 | 0 | 1/1 / 1/1 |
| 2 requisitos, 5 casos: pasó, falló, técnico, bloqueado, pendiente; los iniciados cubren ambos requisitos | 3/5 | 1/2 | 1/5 | 1 | 2/2 / 2/2 |

- [ ] **MET-04 [A§3–5]** Interrupción tras varios pasos de un único caso suma un solo iniciado; casos no alcanzados siguen pendientes. Corridas históricas no se acumulan en la métrica de una corrida. **Prueba UNIT/INT:** duplicados de eventos, dos corridas y un caso con tres pasos.
- [ ] **MET-05 [A§4–5]** Plan vacío nunca recomienda liberar por «todos los obligatorios pasaron» de manera vacua. Ausencia de evaluables no equivale a 100 % de éxito; bloqueos/técnicos/inconclusos que impiden criterio obligatorio dan evidencia insuficiente. **Prueba UNIT:** matrices vacías y mixtas.

## 9. Cierre y decisión de liberación — P1

- [x] **CIE-01 [A§2,§5; U]** `cerrar --plan` y `cerrar --corrida` generan Markdown determinista sin LLM disponible, sin enviar HTTP al objetivo ni lanzar pytest/MCP. Repetir cierre no agrega intentos ni modifica resultados. **Prueba INT:** credenciales ausentes, transporte LLM bloqueado, spies de red/procesos y hash de resultados antes/después.
- [ ] **CIE-02 [A§5]** Informe incluye ambiente, versión, alcance real vs. plan, criterios previos, métricas, defectos, riesgos residuales, desviaciones, limitaciones y recomendación; tablas de ciclo, requisitos y hallazgos por operación. Cada acción indica impacto, evidencia, corrección sugerida y prueba de verificación. **Prueba UNIT:** snapshot semántico de cierre con todos los estados y referencias válidas.
- [x] **CIE-03 [A§5; U]** Criterios se fijan antes de ejecutar y quedan ligados al plan aprobado. ## 11. Ambigüedades originales y decisiones del MVP

La lista inferior conserva las preguntas originales. Los contratos implementados en `docs/API_CONTRACT.md`, el README y el runtime/report definen ya la población completa, prioridad alta obligatoria, precedencia de fallo demostrado, inicio durable, estados, aprobación por hashes, loopback numérico, perfiles revisables y precondiciones declarativas. No equivale a cerrar todas las pruebas adversariales:

- AMB-01/02/04/05: decisiones documentadas y cubiertas por tests de modelos/store/runtime/report más controles E2E.
- AMB-03: confianza local explícita; **no sandbox**, ni garantía frente al dueño de archivos o Python arbitrario lanzado manualmente.
- AMB-06: igualdad estricta distingue entero/decimal/booleano; presencia de ID no demuestra tipo entero positivo, limitación conservada.
- AMB-07: límites de respuesta y secretos conocidos se ejercitan; retención es manual. No se acredita resistencia exhaustiva a disco lleno, todos los patrones de secretos desconocidos ni ataques concurrentes del dueño del registro.

1. **AMB-01 — Población del plan y criterios previos [A§3–5; U].** Falta esquema exacto para separar caso pendiente de automatización de ejecutable, definir `N` cuando hay diseño parcial, guardar criterios/defectos críticos y decidir si «todos los obligatorios» o solo los de prioridad alta gobiernan liberación. No reducir el denominador a scripts generados sin explicarlo. Fijar además precedencia de «Aplazar» frente a «Evidencia insuficiente» si coexisten fallo bloqueante y brecha.
2. **AMB-02 — Intento, interrupción y clasificación [A§3–4].** Definir evento persistido de inicio, estado agregado de corrida y mapeo de JSON inválido, captura ausente, crash durante colección, timeout y pérdida de evidencia. Un bloqueo pre-HTTP no cuenta como intento; un intento de transporte fallido sí. Precisar caso parcialmente ejecutado y cancelación antes de la primera petición, evitando reclasificar historial o inventar evidencia.
3. **AMB-03 — Confianza del pytest directo [A§3; U; S].** Python/pytest ejecuta código antes de una validación dentro del test. Un archivo arbitrariamente editado ejecutado manualmente no puede hacerse seguro con un hash dentro de ese mismo archivo. Delimitar runner/perfil/entorno confiable, verificación anterior a colección, registro fuera del control de la suite y alcance del comando independiente. La aprobación y la equivalencia no pueden desaparecer al pasar de MCP a pytest. No afirmar sandbox de Python si no existe.
4. **AMB-04 — Aprobación y destinos [U; A§2–3].** Se requiere formato/almacenamiento confiable del acto humano, canonicalización de huella y vínculo con suite registrada. Definir si cambiar perfil, URL, operaciones autorizadas, datos de ensayo o versión exige nueva aprobación. La demo debe conservar el mismo plan al cambiar variante, pero eso no debe permitir reutilizar aprobación para otro destino. La excepción SSRF de loopback necesita origen/puerto/IP explícitos, política DNS y redirecciones.
5. **AMB-05 — Precondiciones verificables [A§3; T§1,§6].** No se especifica catálogo declarativo de precondiciones ni quién certifica semilla/versión y datos de entorno. Definirlas sin `eval`, shell o comprobadores Python aportados por plan; la comprobación de bloqueo no debe contactar el objetivo para luego afirmar «cero HTTP».
6. **AMB-06 — Tipos y alcance del catálogo [A§3; T§2–3].** Igualdad estricta necesita definir número entero vs. decimal y formato válido exacto de aserciones/capturas. El catálogo mínimo de status/presencia/igualdad/cuerpo vacío no demuestra por sí solo «ID entero positivo» de TD-01. Declarar esa limitación o acordar comparador tipado; no atribuir a CP-01 una prueba que solo comprueba presencia.
7. **AMB-07 — Depuración y límites operativos [A§2–5; S].** Definir fuentes de secretos y redacción de respuestas que reflejan credenciales antes de persistencia y del LLM. Establecer límite de tamaño de respuesta/evidencia y retención para no agotar disco/memoria con el sistema de ensayo; si se trunca información necesaria, no producir un aprobado sin base. Definir conducta ante disco lleno/escritura parcial conservando resultados ya confirmados.
